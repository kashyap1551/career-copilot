# Plan for Day 5: one name per skill

Goal (docs/SPRINT.md): the same skill gets the same id in every ad and CV, in English and German.

**Where we start (measured, counts only).** Skills come from a 17-entry list (`fixtures/skills.ts`); anything else becomes `new:<slug>`. The AI returns names only and is never shown the list (the prompts do not carry it), so the vocabulary works after the AI, in plain code (`skillIdFor`, used by `fromAd` and `fromCv`). The keys of the ten test ads hold **150 distinct skill names; only 4 are in the list** (121 names in ad-01 to ad-08, 34 in the two holdout ads, with overlap); 62 of the 150 have three or more words ("kinds of experience", not tools). The five CV keys hold 37 names, 12 listed. A vocabulary entry is therefore not one-per-name: many names are the same skill, and some are not skills at all.

## 5.1 A starter vocabulary
**Plain words.** One file of skills. Each has an id (the 17 keep theirs), an English name, a German name, and aliases ("SQL-Kenntnisse", "MS Excel"). A list of "not a skill" phrases (personal traits such as a team player; HANDOFF idea e) sits beside it.
**Code or AI.** The file is data that I draft and you review as a table (the AI writes, code and you decide); the checks are code. No AI at run time. `skillIdFor` learns aliases and one shared `normalizeSkillName` (folds case, accents and ß; hyphens to spaces; drops level and filler words such as advanced, basic, Kenntnisse, Erfahrung, knowledge of; drops a trailing version number). That is a change in lib/engine (careful lane).
**Hand-worked cases first.** (a) Vocabulary validity: ids unique and slug-shaped; every skill has an English name; after folding, no id, name or alias belongs to two skills; the 17 old ids and names unchanged; nothing is both a skill and a not-a-skill phrase. (b) Normalisation: "SQL-Kenntnisse" gives sql; "MS Excel", "Microsoft Excel", "Excel (advanced)" give excel; "Python 3.11" gives python; "Datenanalyse" gives its German entry; case and umlauts do not matter. (c) **Must NOT merge:** Java and JavaScript; C, C++ and C#; SQL, NoSQL, MySQL and SQL Server; R and any word that merely contains r; Power BI and Power Query; Excel and Excellent. (d) The old table E of docs/PLAN-3.1.md changes where an alias now exists ("MS Excel" was `new:ms-excel`): redone by hand and recorded in DECISIONS, not edited to fit the code.
**Check and measure.** SPRINT: every requirement in the test ads has a skill to map to. A call-free script `npm run vocab-check` lists, per ad, requirements, mapped, and unmapped (names for the tuning ads; **counts only for the two holdout ads**). A requirement counts as mapped if its skills are in the vocabulary or its phrase is on the not-a-skill list. Pass: unmapped 0 on the tuning ads and the five CVs; the holdout is reported, not tuned to (see decision 3).
**Risks.** The ids the eval scorers compare change meaning: the CV key matcher and the ad scorer both call `skillIdFor`, so the same AI answer can score differently after 5.1. So the eval fingerprint gets a vocabulary hash (format 3), and old numbers (75 and 76 of 100; CV found 25 and 23) are not comparable and are re-measured. Prompts, schemas and request hashes are untouched: ad `85357f8fac`, CV `193e02ee3f` must still read the same. Data sent anywhere: none. The vocabulary comes from skill names, not ad text; real-ad-derived label files stay gitignored (CLAUDE.md rule 8).
**Names the AI really returns.** The keys hold the names we wrote, not the names the AI returns (the first eval had 46 "name differs"). To build and measure on real AI names, one capture run (about 11 ad calls and 5 CV calls, about 55,000 tokens) saves the raw names to `eval-runs/` (gitignored), with the 3.3 guards. Needs your go at that time (decision 2).

## 5.2 Mapping: alias, close spelling, AI pick, review list
**Plain words.** A name from an ad or CV goes down four steps and stops at the first that is sure: (1) exact alias after normalising; (2) close spelling; (3) the AI picks among candidates; (4) otherwise it goes to a review list and stays unlisted (`new:`), so nothing is guessed.
**Code or AI.** Steps 1, 2 and 4 are code. Step 2: edit distance 0 for names of up to 4 letters, 1 for 5 to 8, 2 for 9 or more; two candidates at the same distance means review. Step 3 is the only AI: one batched call per read with the unmatched names, each with up to 5 candidate skills chosen by code; the AI returns a candidate id or "none"; code rejects any answer not in the candidate list. New prompt, new schema, its own fingerprint (the ad and CV fingerprints stay).
**Hand-worked cases first.** Exact alias; German alias; "Pyhton" gives python; "Tablau" gives tableau; "Exel" (4 letters) is not corrected; "Java Script" gives javascript but never java; a tie goes to review; a candidate not in the list is rejected; an AI "none" gives `new:`; an AI answer for a name that was not asked is ignored; the same name twice in one reading maps once; the order of steps (an exact alias is never overruled by the AI).
**Check and measure.** SPRINT: wrong mappings stay under 5% on the test ads. Rule 6 says counts, so: a label file lists, for every distinct name seen on the test ads and CVs, the expected id or "none"; the script prints mapped right, **wrong**, review and correctly-none, and the limit as a count (5% of the number of names, worked out once the capture run gives it; at 250 names that is 12). Two further pass lines: wrong merges of the "must not merge" set 0, and review at most a count we fix before the run. Stages 1 and 2 are measured first, with no AI; stage 3 is built only if they leave too many unmatched (decision 6).
**Risks.** Stage 3 sends skill names to Groq (new data flow, but names only: no quotes, no CV lines, no ad text; names from a CV can still be unusual). It adds a call per read (one batch, about 1,500 tokens) and latency. Danger of a second 3.3: a prompt tuned on the test names; so one prompt, one run to calibrate, then two counted runs, as in 4.2, with the holdout names as the out-of-sample check. A wrong merge is worse than a miss, so any doubt goes to review. The review list needs a place on the page (names only) and a process: you or I add the alias to the vocabulary; no admin screen.

## 5.3 Store each reading under a hash of the text
**Plain words.** Pasting the same ad again shows the same reading with no second AI call; the same for the CV.
**Code or AI.** All code. Key: SHA-256 (the browser's built-in `crypto.subtle`; no new package) of the text with line endings unified, whitespace collapsed and the ends trimmed (case kept, because quotes are checked against the original text), plus a `READING_VERSION` that changes with the prompt, schema or model. The CV key hashes the numbered, redacted lines. Stored: the checked reading (not the text).
**Hand-worked cases first.** Same text twice: one call, equal results. Extra spaces, a trailing newline or CRLF: same key. One word changed: new key. Empty text: no key, no call. A failed call (429, 5xx, wrong shape) is never stored. A different READING_VERSION: a miss. Capacity 20 readings, oldest out. A test that fails when INSTRUCTIONS or the schema changes without bumping the version (it pins their hash).
**Check and measure.** SPRINT: pasting the same ad twice makes one AI call. Measured with a fake fetch that counts calls (no real call), and once by hand on the live link.
**Risks.** Where it lives (decision 7): page memory now, so a reload clears it and nothing is stored on a device or server; IndexedDB comes with 6.1 behind the same small interface, with consent and delete on 9.3. A stale reading after a prompt change is what READING_VERSION guards. Nothing new is sent anywhere.

## Answers (2026-11-16, owner)
**Decisions 1 to 10: yes, with these changes.**

**Traits (decision 4).** A requirement that is a personal trait stays visible under "Check this yourself" with its quote. It is not counted as a must-have met or missing, and the counts sentence says how many requirements were not counted ("2 requirements were personal traits and were not counted."). Real skills that are soft (Communication, negotiation, teamwork, time management and similar) stay skills in the vocabulary. What has to change:
- **`fromAd` (plain code, careful lane):** a requirement whose every skill name is on the not-a-skill list is taken out of `requirements` and returned, with its quote and importance, in a new `BuildResult.notCounted` list; a requirement that mixes a trait with real skills keeps only the real skills. `fromCv` drops a trait proposed from a CV with a new removal reason "not-a-skill". Hand-worked cases first: all traits; mixed; a trait inside an "or" list; the same trait in another case or in German; a real soft skill that must stay.
- **The engine does not change.** It never sees these requirements, so its must and nice counts leave them out by construction. The `Job` type is untouched (the list lives on `BuildResult`, which the page keeps).
- **The page changes:** "Check this yourself" lists the `notCounted` quotes next to the engine's list, and the counts sentence gets the extra sentence (also in the typed-list mode).
- **You review the not-a-skill list** (the second table of docs/VOCAB-REVIEW.md) before any code uses it; borderline entries are marked.

**Fresh set (decision 3 extended).** Before the final measure of 5.2 you add 3 new ads, at least 2 in German, as a second out-of-sample set (today none of the ten ads is German and one is mixed; four of the five CVs are English and one is mixed). The holdout (ad-09, ad-10) and the fresh set are each measured once, at the end, and the vocabulary is never edited after seeing them. Their names are never used to add aliases before that measure.

**5.2 pass lines, fixed now, before any measure.** Let L be the labelled distinct names of the out-of-sample sets (holdout and fresh set together; each set's numbers are also printed), M the part of L whose expected outcome is a vocabulary skill, `right_M` the names of M mapped to the expected id, and `wrong` the names mapped to a different id, or mapped when the expected outcome is "stay unlisted" or "personal trait". The check passes only if all three hold:
1. **wrong at most 5%:** `wrong <= floor(5 x |L| / 100)` (at |L| = 60 that is 3; at 250 it is 12);
2. **wrong merges 0:** none of the fixed must-not-merge pairs (Java and JavaScript, C, C++ and C#, SQL, NoSQL, MySQL and SQL Server, Power BI and Power Query, Excel and Spreadsheets, R and Rust, and the like, written down before the run) is merged;
3. **recall at least 75%:** `4 x right_M >= 3 x |M|`, so mapping nothing cannot pass.
Review-list names count as not mapped (they lower `right_M`) and are not wrong. In-sample numbers (names the vocabulary was built from) are printed for information only.
**Stage 3 (the AI pick)** is built only if stages 1 and 2 map fewer than 75% of the names in M, in the sense of line 3. Known tension: on in-sample names recall is high by construction, so this test can only show stage 3 is needed, never that it is not. If the single out-of-sample measure then fails line 3, the result is reported as it is, and the next step (stage 3, then a second fresh set) is your decision.

**The 5.1 check ("unmapped 0")** shows coverage on the names the vocabulary was built from. It does not show accuracy; the accuracy question is 5.2's, on names the vocabulary has not seen.

**Level words (decision 10).** When "advanced", "basic" and the like are dropped by normalising, the report note on the page says: "Skill levels (such as advanced) are not compared." (a text change in the page, fast lane; the engine and `fromAd` already ignore levels).
